# 0x2F 0.2.0 — release scope and verification

**Release verification — 2026-11-02.** Target: npm `0x2f@0.2.0`,
Git tag `v0.2.0` and the matching GitHub Release. Public installation and site
availability are checked separately after publication.

Local task runtime for macOS and Linux/POSIX, with one persistent
Linux workspace host and Mac/phone control through existing interfaces. Node.js
≥20 remains the engine contract. Current release qualification uses macOS arm64
Node26.11.1 and Lenovo Ubuntu26.04.1 x86_64 Node26.13.0; older Node-floor checks
remain historical evidence, not fresh runs of this final commit.

## Included

Runtime concurrency/locked publication, occurrence-bound permissions, bounded
remote permission scope, retry/process-group recovery; full TUI request/result/
Verification/input reader; exact next-run note semantics; version-pinned harness
observations including real Codex → Cursor → Codex; portable isolated verifier;
additional persistent Web/phone Light/Dark/System themes; measured-width activity
traces, compact task headings and responsive long-result/header fixes.

ThinkCentre runs the installed candidate as an unprivileged user-systemd
service. The actual node remains `local` to Linux; this does not add a distributed
execution transport. [Host setup](../host-setup.md) documents persistent paths,
explicit PATH, logs, start/stop/restart, security and rollback.

Two host defects found and fixed during real use:

- systemd's default cgroup stop contradicted the detached-worker contract;
  both templates now specify `KillMode=process`. Remote status/errors and CLI
  help now say execution host rather than assuming the host is a Mac.
- LAN pairing killed a managed loopback server, then raced systemd by spawning
  a replacement. Health identifies supervision, templates declare it, and pairing
  now waits for the supervisor. Regression covers return and fail-closed timeout;
  real Lenovo retry returned the service to active with no competing listener.

The phone's plain-HTTP LAN uses the existing pure-JS cryptography fallback.
Actual key derivation took minutes on the physical iPhone; the status now says
it may take a minute or more. No cryptographic parameters were weakened. LAN is
a trusted-network boundary; use separately operated TLS infrastructure otherwise.

## Operator exceptions and archive comparison

The supervisor fixes were authored directly in the release checkout after the
real host reproduced the defects. The executing installation was kept in its
own prefix, then updated only after both runs completed. Rechecks exercised
actual systemd restart and LAN pairing, with deterministic regressions added.
No additional provider run is implied by these direct controller edits.

The two platform-produced gzip archives have different compressed SHA256 values,
but their fully decompressed tar streams are byte-identical, including all file
contents and metadata. The macOS-produced archive is the canonical candidate;
it was additionally transferred to Linux for a clean offline install,77-file
comparison, installed reader PTY and installed Web/CLI checks. No hash mismatch
was ignored. The initial extra Web probe guessed /theme.js and failed404; the
corrected probe reads actual asset routes from installed HTML. This was a test
controller error, not a missing shipped file.

The UI fixture helper initially expected its deliberately uncommitted evidence
directory to exist. Both helpers now create it on a clean checkout. Private
raw evidence remains excluded. The first physical pairing used an incorrect
hardware keyboard layout/grouping; a new unconfirmed test pair and exact
alphanumeric input succeeded. Existing057 trust was never revoked.

## Publication chronology

The initial npm `whoami` checks returned 401, so no publication was attempted.
The owner completed normal npm login; a new `npm whoami` returned the existing
maintainer account. Temporary pending-publication notices were removed and the
canonical package was rebuilt and rechecked because README is a packaged file.

GitHub Actions has no configured release workflow in this repository. The
existing process is manual npm publication, tag/GitHub Release and separate
static-site deployment. Only one verified archive is submitted to npm; registry
metadata and a clean registry installation are checked before promoting the site.
No duplicate CI publisher, force push or branch-protection bypass is used.
