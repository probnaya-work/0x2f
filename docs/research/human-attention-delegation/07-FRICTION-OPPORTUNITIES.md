# 07 — Friction opportunities

Prioritize **truthful access to existing evidence**, then test simplification. Priority reflects demonstrated behavior and consequence, not an invented estimate of minutes saved. Each hypothesis includes a reason to decline and evidence that could change it. None is implemented here.

## P0 / H1 — Restore the TUI's existing task meaning and written result

1. **Evidence/problem:** source, unclipped projection and real PTY show ACCEPT with no written result/verification or full original brief. A no-change investigation has no patch to substitute for its conclusion.
2. **Existing behavior:** detail contains title, run/event history, notes and files; CLI/Web can retrieve the persisted result.
3. **Behavior to investigate:** make the original brief and written result reachable in the TUI at review time; preserve a compact default and explicit full evidence. Start by exposing saved content, not generating a recap.
4. **Human purpose:** remove a forced cross-surface reconstruction path; let the person see what they are accepting.
5. **Risks/tradeoffs:** more content can bury actions; long result needs sensible disclosure/scrolling. A default full transcript would defeat the purpose.
6. **Philosophy:** subtract the need for another surface while retaining industrial typography and a single state-dependent action.
7. **Expected attention effect:** fewer retrieval steps; size/time/comprehension effect unknown.
8. **Validation:** deterministic sentinel checks for original intent and partial-verification warning; real participants evaluate investigation and partial-code tasks in current versus isolated variant. Measure accurate explanation, evidence retrieval, missed limitations and active time.
9. **Reason not to implement / reversal:** a verified reachable result path was missed, or TUI is deliberately retired. If users still need an IDE for code review that does not negate result access, but may limit the broader productivity benefit.

## P0 / H2 — Make intervention scope and input timing truthful

1. **Evidence/problem:** WORKING mobile copy promises current-run influence while `noteWork` only feeds later runs. Synthetic remote permission projection loses a consequential tail/full input while ALLOW remains possible.
2. **Existing behavior:** mobile saves notes; remote projection deliberately strips sensitive/raw tool detail and bounds other fields. Not every retained description is inadequate; real mistaken approval was not observed.
3. **Behavior to investigate:** say when a saved constraint reaches execution. Audit representative existing permission shapes for sufficient operation/target/consequence, and preserve an honest local-review route where the phone cannot establish scope. Do not implement live steering merely to match misleading copy.
4. **Human purpose:** a boundary stated or authorized by the user must correspond to actual machine behavior.
5. **Risks/tradeoffs:** exposing raw inputs can leak sensitive material; blanket extra confirmations can recreate fatigue. “Review on computer” may reduce mobile convenience.
6. **Philosophy:** precise machine affordances, no imagined dialogue or reassuring generated gloss.
7. **Expected attention effect:** fewer false beliefs; may appropriately increase review in consequential cases. Fewer clicks is not the goal.
8. **Validation:** fixture note delivery receipt into next-run prompt; permission matrix with short/long inputs, external paths, complete/incomplete descriptions and unavailable raw scope. Check whether an unfamiliar person correctly identifies timing and authorizes/defers using sufficient evidence. No destructive operations need execute.
9. **Reason not to implement / reversal:** live delivery is demonstrated, or every supported request's retained fields already fully establish consequential scope. That would narrow the change to verified wording; it would not justify exporting more data.

## P1 / H3 — Test a compact return account beneath existing states

1. **Evidence/problem:** intent/results/decisions exist but are distributed; READY accepts partial verification. Retained live utility correction shows why “tests passed” cannot stand in for intent satisfaction.
2. **Existing behavior:** result prose and per-run inspection; no independent assurance or durable human acceptance distinction beyond closure.
3. **Behavior to investigate:** after H1, isolate a presentation of intent, latest result, attributed checks, missing evidence and next action. Use existing text/facts and direct links. Keep five states; preserve full result and actual-current-diff scope.
4. **Human purpose:** reduce reconstruction at the point of assuming responsibility, not maximize perceived automation.
5. **Risks/tradeoffs:** extraction can miss caveats or imply independent verification; a new model summary adds another unverified result. Some tasks do not have executable checks.
6. **Philosophy:** one focused account, trace secondary, no new dashboard/status stack.
7. **Expected attention effect:** cheaper correct reentry is plausible; no measured effect yet.
8. **Validation:** same artifacts and model, counterbalanced current/native/template/variant conditions; genuine multi-hour delay; answer-key score for intent, uncertainty, decisions and next action; defect detection and total active time. Reject on reduced accuracy even if faster.
9. **Reason not to implement / reversal:** existing result/diff or native-plus-template performs equally well; users read more without understanding more; factual fidelity cannot be maintained.

## P2 / H4 — Reduce first-use decisions through honest defaults/diagnostics

1. **Evidence/problem:** absent routing means Claude default; executable “detected and ready” is not authenticated/model-ready; provider failures can require external configuration. No novice prevalence measured.
2. **Existing behavior:** explicit provider override, optional hand-authored AUTO policy; missing binary preflight on CLI.
3. **Behavior to investigate:** show the actual selected provider and what detection established; make auth/config failure remedy and preserved task obvious. Test making ordinary selection implicit within explicit policy before changing defaults.
4. **Human purpose:** one intent should not routinely require registry knowledge.
5. **Risks/tradeoffs:** false auth readiness, hidden approval differences, wrong deterministic provider, preflight cost. Credential-file presence is not authentication proof.
6. **Philosophy:** fewer routine choices, inspectable execution fact; no AI router.
7. **Expected attention effect:** less setup/recovery confusion if it exists in real first use; unknown magnitude.
8. **Validation:** unfamiliar users with only one installed harness, several installed, missing auth and bad model configurations; record actual setup actions/time and correct prediction of what will execute. Use mocks for failure and versioned free diagnostics; no speculative model spend.
9. **Reason not to implement / reversal:** current users already recover cheaply; selection transparency suffices without a default change. This is lower priority than proven misleading affordances.

## P2 / H5 — Explain alert reach before adding alert infrastructure

1. **Evidence/problem:** Web policy deduplicates/batches well; FAILED is quiet, browser notifications target NEEDS YOU, no closed-client push established.
2. **Existing behavior:** a receiving client tracks events; mobile offline visibly disables actions.
3. **Behavior to investigate:** make active-client/host requirements and signaled stops understandable; only then trial failure/digest policy with users who actually miss work.
4. **Human purpose:** fewer manual checks without concealed stalls.
5. **Risks/tradeoffs:** more alerts are more interruptions; OS/browser delivery differs; end-to-end reach needs physical devices.
6. **Philosophy:** retain quiet progress and few meaningful boundaries.
7. **Expected attention effect:** better expectations first; interruption reduction remains unmeasured.
8. **Validation:** active/background/closed browser, TUI-only, offline/reconnect matrix; then real missed-stop detection and unnecessary interruption counts. Use existing receiving-client behavior as control.
9. **Reason not to implement / reversal:** current target users keep the client active and rarely miss actionable stops; added channels create more burden than polling.

## P2 / H6 — Bound context and clarify changing evidence without more orchestration

1. **Evidence/problem:** synthetic prior-run text grows without aggregate budget, repeats Verification and flattens notes; current diff can change after later edits. Same-status dirty paths can evade path observation.
2. **Existing behavior:** comprehensive prior results improve mechanical continuity; no immutable per-run patch/evaluation gate.
3. **Behavior to investigate:** remove duplicate content and preserve human formatting first; document current-diff scope. Only consider bounded projection or stronger change attribution after representative history/shared-checkout cases show need.
4. **Human purpose:** retained history should help the next attempt and explain evidence, not silently dilute constraints or imply causation.
5. **Risks/tradeoffs:** truncation can discard a crucial original constraint; snapshots/patch machinery add storage and conflict semantics. A model compressor can introduce errors.
6. **Philosophy:** subtraction and honest boundaries; keep original artifacts untouched.
7. **Expected attention effect:** less repair/reconstruction if actual long histories fail; stress-probe size is not a latency/token/usability estimate.
8. **Validation:** replay versioned original/notes/prior-result fixtures with explicit early/late constraints and later edits; assert preservation and provenance, then observe actual model behavior only under a new justified hypothesis.
9. **Reason not to implement / reversal:** real tasks rarely accumulate enough history, or available harness context handles it without missed constraints; no blanket compaction feature should ship from a 100-run synthetic example.

## Subtractions to favor

Remove unsupported “session forgets everything” positioning; remove claims a saved note changes an active run; remove “ready” implications from executable-only detection. Make provider/node/session facts secondary for ordinary work. Avoid duplicate verification text in future context work. Keep routine progress silent. Consider retiring a redundant surface if real repeated use cannot justify it; do not remove one solely because a founder prefers another.

Do not remove full evidence, require universal second-agent review, or compress away a meaningful uncertainty in the name of simplicity. Do not rank opportunities with fictional time savings or a single attention score.
